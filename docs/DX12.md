# DirectX 12 support: design notes

Status: **not implemented.** These notes cover what a D3D12 version of the proxy would look like,
what it could and couldn't do, and the order to build it in.

## Why it matters

Current Siege runs on DirectX 12 only. Ubisoft replaced Vulkan with DX12 in Operation Twin Shells
(Y9S3), then removed DX11 with Operation Prep Phase (Y10S1, early 2025). Siege X (June 2025)
requires DX12 on every hardware tier, and the old launch options that forced DX11 no longer work.

So the `d3d11.dll` proxy does nothing in current Siege: the game never loads D3D11. It still works
for older builds that had DX11, which the per-build folders already support.

## Why the D3D11 approach doesn't carry over

In D3D11, `ID3D11Device::CreateTexture2D` gets the description and the pixels in one call
(`proxy/texture_hook.cpp`). The proxy hashes the data, looks up a mod and creates a different
texture before the game ever sees a pointer.

D3D12 splits this into three steps:

1. **Create the texture** with `CreateCommittedResource` / `CreatePlacedResource`. It takes a
   description only: no data, so no hash.
2. **Write the pixels** into a CPU-visible upload buffer that the game manages itself.
3. **Record a copy** (`CopyTextureRegion`) from that buffer into the texture. The GPU runs it
   later, after `ID3D12CommandQueue::ExecuteCommandLists`.

By the time the data can be hashed, the game already holds the `ID3D12Resource` and has
probably created descriptors (SRVs) for it.

## Design

A `d3d12.dll` proxy, built the same way as the D3D11 one: pass-through exports generated from an
exports list, the real DLL loaded lazily from System32 (or `ori_d3d12.dll` when chaining), and
vtable patches instead of wrapper objects.

| Hook | vtable slot | Purpose |
|---|---|---|
| `D3D12CreateDevice` (export) | — | Install the hooks below on the new device |
| `ID3D12Device::CreateCommittedResource` | 27 | Remember which resources are 2D textures, with their descriptions |
| `ID3D12Device::CreatePlacedResource` | 29 | Same, for resources placed in a heap |
| `CreateCommittedResource1/2/3`, `CreatePlacedResource1/2` (Device4, Device8, Device10) | — | Same, for the newer interfaces |
| `ID3D12GraphicsCommandList::CopyTextureRegion` | 16 | Record "buffer + footprint → texture subresource" per command list; clear on `Reset` |
| `ID3D12CommandQueue::ExecuteCommandLists` | 10 | The data is final now: hash, dump, replace, then forward the call |

The slot numbers come from the declaration order in `d3d12.h`. Check them against the header
before relying on them.

The rest of the proxy carries over unchanged: `Runtime`, the hash index, the folder watcher,
the dump thread, settings, and every DDS file and mod pack.

Command lists can be recorded on several threads at once, so recorded copies are kept per
command list, which keeps locking light.

## What each feature costs

- **Dumping: straightforward.** In the `ExecuteCommandLists` hook, read the upload buffer at the
  recorded footprint and queue it to the existing dump thread.
- **Replacing with a mod of the same size, format and mip count: moderate.** Either overwrite the
  upload buffer's bytes before forwarding the call, or submit a small command list of our own
  after the game's lists that copies the mod data in. The game's resource and descriptors stay
  valid.
- **Replacing with a mod of a different size or mip count: hard.** Mods are often higher-resolution
  than the original, so this case matters. The game's resource is already the wrong size, so we
  would have to:
  - create the replacement resource ourselves and keep it in a shader-readable state, and
  - redirect every descriptor that points at the original, by hooking `CreateShaderResourceView`,
    `CopyDescriptors` and `CopyDescriptorsSimple`, and adjusting MipLevels in the SRV
    description.

  Bindless engines that copy descriptors every frame make this costly and fragile. Placed
  resources sharing a heap, residency (`Evict` / `MakeResident`) and tiled resources add more
  edge cases.

## Hash compatibility

The hash is 1 + the sum of the bytes over `SysMemSlicePitch` of mip 0 (`core/resorep_hash.h`).
D3D12 upload rows are padded to 256 bytes (`D3D12_TEXTURE_DATA_PITCH_ALIGNMENT`), so hashing the
buffer as-is would give different hashes from D3D11.

Hashing only the real bytes of each row, skipping the padding, should give the same hash as
D3D11 for the same texture, so existing packs would keep working. That assumes the D3D11 builds
passed tightly packed rows. Verify it by comparing dumps from an old DX11 build and a DX12 build.

## Risks

- **Slow reads.** Upload heaps are write-combined, so reading them from the CPU is slow, and every
  texture upload would be read once to hash it. Streaming loads (`MOVNTDQA`) help. Measure level
  load times before committing to this.
- **GPU upload heaps (ReBAR).** CPU reads from these are slower still.
- **DirectStorage with GPU decompression.** The CPU only sees compressed data, so textures can't be
  hashed or dumped. There is no workaround at this layer.
- **Anti-cheat.** The same caveat as the D3D11 proxy applies: BattlEye can flag a replacement DLL.

## What to check on a Siege install first

- **DirectStorage:** look for `dstorage.dll` or `dstoragecore.dll` in the game folder. If they are
  there, check whether textures go through GPU decompression, because that would rule this
  approach out for those textures.
- **Agility SDK:** look for a `D3D12` subfolder with `D3D12Core.dll`, or a `D3D12SDKVersion`
  export in `RainbowSix.exe` (`dumpbin /exports RainbowSix.exe`). This doesn't block the proxy:
  the System32 `d3d12.dll` reads those exports from the game's exe, not from the proxy.

## Loading the proxy

A `d3d12.dll` in the game folder that forwards to System32's copy, like the D3D11 proxy.
A `dxgi.dll` proxy would see the command queue when the swap chain is created, but only after
the device exists, so textures uploaded before that would be missed.

## Tests

WARP supports D3D12 (`IDXGIFactory4::EnumWarpAdapter`), so a D3D12 version of `proxy_test` can
cover replacement, dumping and hot reload, like the existing test does on a D3D11 WARP device.

## Manager changes

These are small:

- The **Games** tab reads the exe's import table to see whether it uses `d3d11`, `d3d12` or
  `vulkan-1`, and installs the matching proxy.
- The analyzer and previews can stay on D3D11: DDS files don't depend on the game's API.

## Suggested order

1. A D3D12 proxy with dumping and same-size replacement only, plus a WARP test.
2. Measure the cost of hashing on real games, Siege in particular.
3. Only then decide whether descriptor redirection, needed for mods of a different size, is worth
   its complexity.
